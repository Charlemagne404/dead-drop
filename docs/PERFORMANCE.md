# Drop performance benchmark

The command/test-layer map is in [`TESTING.md`](TESTING.md); this document
defines benchmark cases, controls, and interpretation.

`npm run perf` is the local comparison command for transfer and peer-registry
performance. It builds the feature-gated `performance_peer` helper in the
optimized Rust profile, creates all inputs at runtime, and removes them when
each test process exits. No benchmark fixture is checked in.

The runner starts a fresh receiver and sender for each case. The receiver
prints its ephemeral loopback endpoint; the sender generates the requested
files, measures a standalone SHA-256 pass and a TCP connection probe, then
uses the production transfer listener, framing, staging, verification, and
finalization paths. Process-to-ready timings provide a repeatable startup proxy
for the benchmark helper, and the two processes are sampled independently every
100 ms with the host `ps` command.

Cases and controls

- `zero-bytes`, `one-byte`, `four-kib`, `one-mib`, `one-hundred-mib`, and
  `larger-generated` exercise one file at each size.
- `many-small-files` defaults to 64 files of 4 KiB each.
- The registry case applies one endpoint observation to 10,000 synthetic
  peers, then times the normal snapshot and diagnostics projections.
- `DROP_PERF_LARGE_BYTES`, `DROP_PERF_SMALL_FILE_COUNT`,
  `DROP_PERF_SMALL_FILE_BYTES`, and `DROP_PERF_PEER_COUNT` override generated
  sizes/counts. `DROP_PERF_PROFILE=debug` selects a debug helper build for
  quick iteration; release numbers are the comparison baseline.
- `npm run perf -- --json` emits one JSON document suitable for archiving or
  comparing without adding a repository artifact.

Metric definitions

- `prepare_and_request_ms` includes local metadata, sender SHA-256 preparation,
  connection/identification, and request delivery to the waiting-for-acceptance
  phase. `sha256_ms` is a separately timed read/hash pass over the same
  generated inputs; `sha256_to_prepare_ratio_percent` compares that cost with
  the preparation interval. It is a diagnostic ratio from separate passes and
  can exceed 100% when scheduling or filesystem cache state differs.
  `connection_ms` is a loopback TCP connect probe.
- `receiver_process_ready_ms` measures helper process start through listener
  readiness. `sender_process_to_start_ms` measures helper process start through
  completion of input generation and the standalone hash pass. These are
  startup proxies, not installed Tauri/WebView startup measurements.
- `accepted_to_terminal_ms` covers the accepted transfer, receiver staging and
  hashing, finalization, and the terminal event. `transfer_mbps` is total
  generated bytes divided by sender wall time, including preparation;
  `accepted_transfer_mbps` uses the accepted-to-terminal interval and is the
  better sustained-transfer comparison, though it still includes receiver
  verification and finalization.
- Sender and receiver `cpu_percent_max` and `rss_kib_max` are sampled from
  their separate helper processes. Very short cases may have no 100 ms sample;
  those values are reported as `null`, not zero.
- `progress_events` counts production transfer snapshots whose phase is
  `transferring`. `progress_event_rate_hz` is the sender count divided by the
  accepted-to-terminal interval. `frontend_progress_render_upper_bound_hz`
  uses all sender `transfer-update` snapshots, because each can cause one
  frontend state update while the transfer panel is mounted. React batching
  can make the observed paint rate lower.
- Registry timings cover the current merge and projection APIs, not Tauri IPC
  serialization or a WebView paint.

This is a local loopback and local-filesystem benchmark. It does not prove
physical LAN/Wi-Fi/VPN throughput, firewall behavior, installed Tauri/WebView
startup, or platform-specific filesystem behavior. Idle discovery is governed
by the source worker intervals in `src-tauri/src/discovery.rs`; a native
installed-app idle sample still requires running the app on the target host.
